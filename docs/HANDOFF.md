## 1. 開発上の最優先ルール

以下はユーザーが指定した開発ルールであり、今後の作業でも優先する。

1. 既存のデザイン、配色、フォント、レイアウト、操作性を維持する。明確な承認なしに変更しない。AI文章生成の改善を理由に画面デザインを変更しない。
2. 既存機能を削除・変更する場合は事前承認を得る。
3. 最優先の開発課題は、集客・予約・販売につながるAI文章の品質改善とする。AIDA、PASONA、BABなどを販促目的に応じて内部の文章設計に活用する。
4. 3つの販促プランは、単なる言い換えではなく、異なる販売アプローチにする。
5. POP・LINE・Instagramは、それぞれの媒体に適した訴求と文章構成にする。
6. 入力されていない価格、割引、効果、実績、限定性などを創作しない。
7. 特定のエステサロンに限定せず、各サロンの設定に応じた文章を生成する。
8. 開発は作業用ブランチで行い、Previewで確認してから本番反映する。
9. ChatGPTに戻して開発を継続できるよう、作業ブランチ・変更履歴・判断理由・検証結果・残課題を継続的に記録する。
10. 本番環境、Supabaseのデータ、デザインに影響する操作は事前承認を得る。
11. AI文章の品質改善以外の修正候補は記録するが、別途承認されるまで着手しない。

**今回の許可範囲は、この資料の作成のみ。** アプリ本体、API、デザイン、DB、環境設定の変更、コミット、プッシュ、デプロイは許可されていない。構成案や本資料の承認を、個別の実装変更や本番反映の承認として扱わない。

## 5. 最優先課題：AI文章の品質改善

### 改善する課題

ユーザー報告にある「抽象的な文章」「具体的メリット・行動理由の弱さ」を中心に改善する。単なる文章量の増加や美辞麗句の追加を品質改善としない。

入力情報とサロン設定を根拠に、次のつながりを明確にする。

1. 誰の、どのような悩み・関心・利用場面に向けた提案か。
2. 入力された特徴が、その顧客にどのような価値を持つか。
3. なぜその商品・メニュー・サロンを選ぶのか。
4. 来店・予約・購入へ、どのように自然につなげるか。

「今行動する理由」は入力された期間・条件・利用場面等を根拠にする。残席、締切、限定性、人気、効果保証などを創作して補わない。情報が不足する場合も、事実を追加せず表現できる範囲で設計する。

### 内部の文章設計

- AIDA：注意・興味・欲求から行動までの流れが適する場合に活用する。
- PASONA：顧客の悩みへの共感と提案をつなぐ場合に活用する。過剰な不安喚起はしない。
- BAB：顧客が望む状態と提供価値をつなぐ場合に活用する。未入力の効果や変化を実証済みの事実として表現しない。

これらは内部設計の補助であり、手法名や構成ラベルを利用者向け文章に表示する必要はない。全文章に同じ型を機械的に当てはめない。

### 3つの販促プラン

顧客の悩み、利用場面、体験価値など、入力から導ける異なる入口を設計し、販売アプローチの違いが利用者に分かるようにする。同じ悩みを言い換えた3案にしない。推薦理由は今回の目的・対象・内容と結び付ける。

### 媒体別の役割

| 媒体 | 改善の観点 |
| --- | --- |
| POP | 短時間で対象・価値・販促内容が伝わる見出しと簡潔な説明。既存の表示領域・デザインを維持する |
| LINE | 自分に関係がある導入、具体的な価値・選ぶ理由、条件、自然な行動案内。スマートフォンで読みやすい段落 |
| Instagram | 冒頭で関心を引き、悩み・利用場面・提供価値・体験への期待から行動案内へつなぐ。投稿文とハッシュタグの役割を分ける |

現在の文章APIはLINEを320〜480文字程度、Instagramを500〜700文字程度と指示している。短文・絵文字不足時に一度修正生成する処理があるが、全条件を最終的に保証する仕組みではない。長さだけで合否を判断しない。

### ChatGPTへ開発を戻す具体的な手順

1. **Codexでの作業を停止する。** 引き継ぎに入ることを明示し、新たな編集・コミット・プッシュ・デプロイを開始しない。進行中の操作があれば状態を確認し、安全に停止または完了した結果を記録する。
2. **ローカルの状態を読み取り確認する。** `git branch --show-current`、`git rev-parse HEAD`、`git status --short`、`git diff`、`git diff --cached` で、作業ブランチ、完全なコミットID、未ステージ・ステージ済みの変更を確認する。未追跡ファイルはdiffに内容が出ないため、ファイル一覧と内容を別途確認する。引き継ぎのために変更を破棄・リセットしない。
3. **検証結果と残課題を整理する。** 実施したチェック、対象コミット・入力、成功・失敗・未実施、Previewでの確認結果、判断理由、保留事項、必要な承認、次に行う作業をまとめる。今回のような資料のみの作業は、アプリを再検証していないことを明記する。
